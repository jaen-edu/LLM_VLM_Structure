# HTTPS 기반 대안 가이드: SSH가 막힌 학교 환경에서 RunPod 실습 운영하기

## 1. 이 문서의 목적

이 문서는 다음 상황을 대비한 대안 문서입니다.

- 학교 방화벽 때문에 SSH 접속이 원활하지 않음
- 외부 22번 포트뿐 아니라 임의의 외부 고포트까지 차단될 수 있음
- 학생 15명이 강사가 준비한 RunPod Pod에 접속해야 함
- 가능하면 브라우저와 HTTPS만으로 실습을 진행하고 싶음

핵심 결론은 아래와 같습니다.

1. **노트북 중심 수업**이면 `JupyterLab`이 가장 현실적입니다.
2. **코드 편집 중심 수업**이면 `브라우저 IDE(OpenVSCode Server 또는 code-server 계열)`가 가장 실용적입니다.
3. **긴급 복구용**으로는 `RunPod Web Terminal`이 가장 빠릅니다.
4. `VS Code Remote Tunnels`도 가능하지만, **1명의 강사가 15명의 학생 Pod를 운영하는 수업**에서는 계정과 권한 관리 때문에 기본안으로 권장하기 어렵습니다.

## 2. 왜 HTTPS 대안이 필요한가

기존 문서의 기본안은 `SSH over exposed TCP`입니다. 이 방식은 학교가 22번만 막고 외부 고포트는 허용하면 잘 동작합니다.

하지만 아래 상황에서는 HTTPS 기반 대안이 필요합니다.

1. `Test-NetConnection <IP> -Port <외부포트>` 결과가 `False`로 나오는 경우
2. 학교 보안 장비가 임의의 SSH 트래픽 자체를 차단하는 경우
3. 수업 PC마다 SSH 설정이 꼬여 현장 지원 비용이 커지는 경우
4. 학생 PC에 설치 작업을 최소화하고 브라우저만으로 진행하고 싶은 경우

## 3. 빠른 선택표

| 방식 | 통신 방식 | 학생 준비물 | 강사 준비 난이도 | 수업 적합도 | 권장 상황 |
| --- | --- | --- | --- | --- | --- |
| RunPod Web Terminal | HTTPS | 브라우저 | 매우 낮음 | 낮음 | 긴급 점검, 간단한 명령 |
| JupyterLab | HTTPS 프록시 | 브라우저 | 낮음 | 높음 | Python, 데이터 분석, ML 노트북 |
| 브라우저 IDE | HTTPS 프록시 | 브라우저 | 중간 | 높음 | 파일 편집, 프로젝트 실습 |
| VS Code Remote Tunnels | HTTPS + 계정 인증 | 브라우저 또는 VS Code | 높음 | 중간 | 고급 운영, 소규모 파일럿 |

## 4. 이 수업에 대한 권장 운영 순서

강사 1명, 학생 15명 수업 기준으로는 아래 순서를 권장합니다.

### 권장안 A: 노트북 중심 수업

1. 기본안: `JupyterLab`
2. 보조안: `Web Terminal`

### 권장안 B: 프로젝트 파일 편집 중심 수업

1. 기본안: `브라우저 IDE`
2. 보조안: `Web Terminal`

### 권장안 C: SSH와 가장 비슷한 원격 개발 경험이 꼭 필요한 경우

1. 소규모 사전 검증 후 `VS Code Remote Tunnels`
2. 실패 시 `브라우저 IDE`로 즉시 전환

## 5. 공통 네트워크 전제

HTTPS 대안은 대체로 443 포트만 열려 있으면 사용할 수 있습니다. 다만 실제 학교망에서는 아래 요소도 확인해야 합니다.

1. 브라우저에서 `https://console.runpod.io` 접속 가능 여부
2. 브라우저에서 `https://*.proxy.runpod.net` 접속 가능 여부
3. WebSocket을 쓰는 서비스가 차단되지 않는지 여부
4. 사내 SSL 검사 장비가 장기 연결을 끊지 않는지 여부

`VS Code Remote Tunnels`를 쓰는 경우에는 추가로 아래 도메인 접근이 필요할 수 있습니다.

1. `https://vscode.dev`
2. `https://global.rel.tunnels.api.visualstudio.com`
3. GitHub 또는 Microsoft 로그인 관련 도메인

## 6. 방식 1: RunPod Web Terminal

## 개요

RunPod 콘솔 안에서 바로 여는 브라우저 기반 터미널입니다. 별도 포트 노출 없이 HTTPS로 접근합니다.

RunPod 공식 설명에서도 `quick access` 용도로 안내하며, 장시간 개발 환경보다는 빠른 점검용에 가깝습니다.

## 장점

1. 학생 PC에 설치가 거의 필요 없습니다.
2. 포트 노출 설정이 필요 없습니다.
3. SSH 설정 오류가 없습니다.

## 단점

1. VS Code 같은 편집 경험은 없습니다.
2. 장시간 작업에 불편합니다.
3. 여러 파일을 다루는 실습에는 비효율적입니다.

## 강사용 준비 절차

1. Pod를 실행합니다.
2. RunPod 콘솔에서 Pods 페이지로 이동합니다.
3. 대상 Pod에서 `Connect`를 클릭합니다.
4. `Open Web Terminal`이 정상 동작하는지 확인합니다.
5. 학생별 Pod 배정표를 만듭니다.
6. 학생이 사용할 RunPod 콘솔 접속 방식까지 포함해 안내합니다.

## 학생용 접속 절차

1. 강사가 안내한 RunPod 콘솔 경로에 접속합니다.
2. 자신의 Pod를 선택합니다.
3. `Connect`를 클릭합니다.
4. `Open Web Terminal`을 엽니다.
5. `/workspace`에서 실습을 진행합니다.

## 적합한 수업 유형

1. 리눅스 기본 명령 실습
2. Python 스크립트 한두 개 실행
3. 환경 점검
4. 긴급 장애 대응

## 비권장 상황

1. 여러 파일을 오가며 편집해야 하는 프로젝트형 수업
2. 디버깅, 확장 설치, 코드 탐색이 중요한 수업

## 7. 방식 2: JupyterLab

## 개요

RunPod는 공식 PyTorch 계열 템플릿에서 JupyterLab을 기본 제공하는 경우가 많습니다. 브라우저에서 HTTPS로 접속하므로, SSH가 막힌 환경에서 가장 안정적인 대안입니다.

RunPod 문서 기준으로는 `Connect` 메뉴의 `HTTP Services` 아래에서 `Jupyter Lab` 링크를 열어 사용합니다. 보통 내부 포트는 `8888`입니다.

## 장점

1. 설치 부담이 가장 적습니다.
2. Python, 데이터 분석, GPU 실습에 잘 맞습니다.
3. 파일 브라우저, 노트북, 터미널을 한 화면에서 사용할 수 있습니다.

## 단점

1. 일반 IDE보다 코드 탐색 경험이 약합니다.
2. 대형 프로젝트 구조를 편집하기에는 불편합니다.
3. 실습이 `.ipynb`에 치우치기 쉽습니다.

## 강사용 준비 절차

1. JupyterLab이 포함된 공식 RunPod 템플릿을 선택합니다.
2. 테스트 Pod 1개를 먼저 띄웁니다.
3. `Connect > HTTP Services > Jupyter Lab` 링크가 정상 동작하는지 확인합니다.
4. 수업용 Pod 16개를 동일 템플릿으로 준비합니다.
5. 학생별 Pod와 접속 링크를 정리합니다.
6. 브라우저에서 노트북 실행, 터미널 실행, 파일 저장이 모두 되는지 확인합니다.

## 학생용 접속 절차

1. 강사가 준 JupyterLab 링크를 엽니다.
2. JupyterLab이 열리면 왼쪽 파일 브라우저에서 `/workspace`를 확인합니다.
3. 새 노트북이나 새 파일을 만들어 실습을 진행합니다.
4. 필요한 경우 JupyterLab의 Terminal 기능을 함께 사용합니다.

## 운영 팁

1. 실습 자료가 노트북 위주라면 가장 먼저 고려합니다.
2. 학생에게는 `.ipynb`와 `.py` 저장 위치를 모두 `/workspace`로 통일하게 합니다.
3. JupyterLab 링크가 오래 비어 있으면 Pod를 다시 확인하고, 필요하면 재시작 전에 예비 Pod 전환을 우선 고려합니다.

## 주의 사항

1. 강사는 반드시 **학생별 링크가 올바른 Pod로 연결되는지** 확인해야 합니다.
2. 단순한 프록시 URL만 외부에 노출하기보다, 실제 접속 흐름을 사전 테스트한 뒤 배포해야 합니다.
3. 인증이 없는 HTTP 서비스는 그대로 공개하지 않는 것이 좋습니다.

## 적합한 수업 유형

1. Python 기초
2. 데이터 분석
3. 머신러닝 실습
4. GPU 연산 확인

## 8. 방식 3: 브라우저 IDE

## 개요

SSH 대신 브라우저에서 VS Code와 비슷한 편집기를 띄우는 방식입니다. 수업 목적이 `파일 편집`, `프로젝트 구조 탐색`, `터미널 + 에디터 동시 사용`이라면 HTTPS 대안 중 가장 실용적입니다.

대표 후보는 아래와 같습니다.

1. `OpenVSCode Server`
2. `code-server`

두 도구 모두 원격 서버에서 IDE를 실행하고, 학생은 브라우저로 접속합니다.

## 이 수업에서의 권장안

강사가 16개 Pod를 동일하게 관리해야 하므로, 하나를 정해서 템플릿에 고정하는 것이 중요합니다. 이 문서에서는 예시로 `OpenVSCode Server`를 기준으로 설명합니다.

## 장점

1. 학생 PC에 별도 IDE 설정이 거의 필요 없습니다.
2. 브라우저만으로 편집, 파일 탐색, 터미널 사용이 가능합니다.
3. SSH가 막혀도 443 기반 프록시로 우회할 수 있습니다.

## 단점

1. 강사가 템플릿과 인증을 미리 구성해야 합니다.
2. 공용 URL이므로 인증 설정을 반드시 해야 합니다.
3. 데스크톱 VS Code와 완전히 같지는 않습니다.

## 강사용 준비 절차

### 1. 공통 템플릿 결정

1. 실습용 베이스 이미지 또는 템플릿을 하나 정합니다.
2. 모든 Pod를 동일한 구성으로 맞춥니다.

### 2. HTTP 포트 노출

브라우저 IDE가 사용할 내부 포트를 하나 정합니다. 예시는 `3000`입니다.

1. Pod 템플릿 또는 Pod 설정에서 `Expose HTTP Ports`에 `3000`을 추가합니다.
2. 브라우저 IDE는 반드시 `0.0.0.0`으로 바인딩해야 합니다.

RunPod 프록시 URL 형식은 아래와 같습니다.

```text
https://[POD_ID]-3000.proxy.runpod.net
```

### 3. OpenVSCode Server 설치 및 실행 예시

OpenVSCode Server 공식 문서 기준으로 Linux 환경에서는 압축 파일을 내려받아 실행할 수 있고, 원격 접근 시 `--host 0.0.0.0`, 보안용으로 `--connection-token` 사용을 권장할 수 있습니다.

예시 흐름:

```bash
cd /workspace
# 최신 릴리스 버전에 맞게 파일명은 조정
tar -xzf openvscode-server-<VERSION>-linux-x64.tar.gz
cd openvscode-server-<VERSION>-linux-x64
./bin/openvscode-server --host 0.0.0.0 --port 3000 --connection-token STUDENT_TOKEN
```

실무적으로는 이 명령을 웹 터미널에서 매번 수동 실행하지 말고, **Pod 시작 스크립트나 템플릿 시작 명령에 포함**하는 것이 낫습니다.

### 4. 학생별 인증 구성

강사는 아래 중 하나를 선택합니다.

1. 학생별 서로 다른 토큰 사용
2. 수업 공통 토큰 사용 후 학생별 URL만 분리

보안상으로는 학생별 토큰이 더 낫습니다.

### 5. 배포 전 테스트

1. 브라우저에서 실제 URL 접속 확인
2. 토큰 인증 확인
3. `/workspace`가 기본 작업 위치로 적절한지 확인
4. 새 파일 생성, 저장, 터미널 실행 확인

## 학생용 접속 절차

1. 강사가 제공한 HTTPS URL을 엽니다.
2. 토큰 또는 비밀번호를 입력합니다.
3. 브라우저 IDE가 열리면 `/workspace` 폴더를 엽니다.
4. 터미널을 열어 필요한 명령을 실행합니다.
5. 파일은 모두 `/workspace` 아래에 저장합니다.

## 운영 팁

1. 학생용 문서는 브라우저 URL, 인증 정보, `/workspace` 사용 규칙만 간단히 주는 편이 좋습니다.
2. 강사는 시작 스크립트와 포트 노출을 한 번에 템플릿화해야 16개 Pod 운영이 편해집니다.
3. 수업 자료가 여러 파일로 된 프로젝트라면 JupyterLab보다 이 방식이 낫습니다.

## code-server를 선택해도 되는가

가능합니다. `code-server`도 브라우저에서 VS Code 계열 편집기를 제공하며, 공식 문서 기준으로 설치 스크립트 방식과 자체 인증 구성을 지원합니다.

다만 수업에서는 **한 가지 도구만 표준으로 고정**하는 것이 중요합니다. 혼합 운영은 현장 지원 비용만 늘립니다.

## 적합한 수업 유형

1. Python 프로젝트 구조 실습
2. 여러 파일을 편집하는 웹/API 기초 실습
3. Git과 파일 탐색을 함께 쓰는 실습

## 9. 방식 4: VS Code Remote Tunnels

## 개요

VS Code는 SSH 없이도 원격 머신에 접속할 수 있는 `Remote Tunnels` 기능을 제공합니다. 원격 머신에서 `code tunnel`을 실행하면, 학생은 브라우저의 `vscode.dev` 또는 로컬 VS Code로 접속할 수 있습니다.

이 방식은 네트워크 측면에서는 매력적입니다. 문서 기준으로는 대체로 아웃바운드 HTTPS 연결만 있으면 되고, 별도 SSH 리스너를 열 필요가 없습니다.

## 장점

1. SSH 포트 개방이 필요 없습니다.
2. VS Code와 비교적 가까운 경험을 제공합니다.
3. 브라우저와 데스크톱 클라이언트 모두 연결이 가능합니다.

## 단점

1. 터널 호스팅과 접속 모두 GitHub 또는 Microsoft 계정 인증이 필요합니다.
2. 문서 기준으로 한 원격 인스턴스는 동시에 여러 사용자/클라이언트가 함께 쓰는 용도로 설계되지 않았습니다.
3. 강사 1명이 학생 15명 Pod를 계정까지 포함해 중앙 운영하기에는 관리 부담이 큽니다.

## 이 수업에서 기본안으로 권장하지 않는 이유

가장 큰 이유는 **계정 귀속 문제**입니다.

VS Code 문서 기준으로 터널을 호스팅하는 쪽과 접속하는 쪽은 같은 GitHub 또는 Microsoft 계정 체계의 인증이 필요합니다. 따라서 아래 운영 방식이 필요합니다.

1. 학생이 자기 계정으로 자기 Pod 터널을 쓰는 방식
2. 강사가 여러 계정을 별도로 관리하는 방식

둘 다 일반 수업 운영에는 부담이 큽니다.

## 그래도 고려할 수 있는 경우

1. 학생 수가 적은 파일럿 수업
2. 학생 전원이 GitHub 또는 Microsoft 계정을 이미 가지고 있음
3. 강사가 사전 자동화까지 준비할 수 있음
4. 브라우저 IDE보다 데스크톱 VS Code 경험이 꼭 필요함

## 강사용 준비 절차 개요

1. Pod 안에 VS Code CLI를 준비합니다.
2. Pod에서 `code tunnel`을 실행합니다.
3. GitHub 또는 Microsoft 계정으로 로그인해 터널을 등록합니다.
4. 학생이 같은 계정 체계로 `vscode.dev` 또는 VS Code에서 연결합니다.

## 운영 결론

기술적으로는 유효한 HTTPS 대안이지만, **이 수업 규모에서는 브라우저 IDE보다 운영 부담이 크다**고 보는 것이 맞습니다.

## 12. 학생 안내문에 꼭 넣어야 할 문장

강사가 학생에게 HTTPS 대안을 안내할 때는 아래 내용을 꼭 포함하는 것이 좋습니다.

1. 본인에게 배정된 URL만 사용하세요.
2. 파일은 반드시 `/workspace`에 저장하세요.
3. 접속이 끊기면 새로고침 전에 강사에게 먼저 알리세요.
4. 토큰이나 비밀번호를 다른 학생과 공유하지 마세요.

## 13. 최종 추천

이 수업 조건에서는 아래처럼 정리하는 것이 가장 현실적입니다.

1. **SSH 기본안 유지**: 가능하면 기존 `SSH over exposed TCP` 사용
2. **HTTPS 1순위 대안**: 노트북형 수업이면 `JupyterLab`
3. **HTTPS 2순위 대안**: 편집형 수업이면 `브라우저 IDE`
4. **긴급 복구용**: `RunPod Web Terminal`
5. **고급 선택지**: `VS Code Remote Tunnels`는 파일럿 운영 후 도입 검토
